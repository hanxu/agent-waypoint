# 决策记录（append-only）

## [2026-10-29] 页面看板采用"注入式单文件 HTML"，而非独立前端工程或本地 API 前端

- 备选方案：A 单文件 HTML（生成时把 `board --json` 注入模板）；B 独立 SPA（Vite/React）+ 本地 API；C 终端 TUI
- 选择及原因：A。页面只需只读展示，数据量是十几个会话；单文件可离线双击、可丢给别人看、无需 node/构建链，符合"运行期零依赖"的项目前提；C 不够直观（用户明确说命令行不直观）
- 放弃方案的原因：B 引入 node 工具链与新依赖面，与项目的零依赖卖点冲突，且打包产物的可移植性反而不如单文件；C 已判定不满足"直观"

## [2026-10-29] 看板数据源唯一为 `board --json`，页面不二次采集

- 备选方案：页面直接读 `~/.waypoint/tasks/**` 与 `repos.txt`；或经 `board --json`
- 选择及原因：经 `board --json`。命令行与页面共用同一份契约，字段语义只在一处维护，避免两份实现的漂移；`--json` 因此升格为稳定输出契约（PROTOCOL §7）
- 放弃方案的原因：页面自采会与 shell 里的陈旧判定/锁解析/时间归一化逻辑重复实现，必然不同步

## [2026-10-29] `--serve` 作为可选形态，依赖 python3 标准库

- 备选方案：只做静态快照；或用 python3 标准库起本地服务提供实时刷新
- 选择及原因：两者都做。静态满足"离线/转发/零依赖"，`--serve` 满足"边干活边看它变"；服务只用标准库、只绑 127.0.0.1，缺 python3 时明确提示回退静态
- 放弃方案的原因：只做静态会让"看板"变成需要手动重新生成的快照；只做服务则把零依赖卖点绑死在 python3 上

## [2026-10-29] 不清 `1da636e` 之后的历史，用 `git reset --soft`

- 备选方案：`git reset --hard 1da636e`；`--soft`；`revert` 已 revert 的提交；保留现状
- 选择及原因：`--soft`。HEAD 与 `1da636e` 内容等价（`git diff` 为空），soft 只移 HEAD、工作区改动完整保留，历史恢复干净后一次性提交本轮成果
- 放弃方案的原因：`--hard` 会连带丢弃未提交的本轮改动（我最初的口头建议是错的）；再 revert 只会继续堆噪音
